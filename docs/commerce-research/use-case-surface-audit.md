> client purity (`route-paths`), entity brands on money paths, additive error

>
> How to read rows in ≤30s:
> - `ready-for-service` / `contract-only` / `partial` describe **2024–early research
>   intent**, not today's open work.
> - “Gaps to test or fix” are optional host-integration notes unless a live
>   ROADMAP/follow-up card still tracks them.
> - Superseded examples: registry pins, `/types` barrel, `/client` purity,
>   Astro `^7` peer honesty, EmDash storage converters, branded cart/checkout/order
>   ids — all shipped; do not re-open as “must implement.”

This file is a numbered audit of Mika's public contracts, copyable UI, EmDash
collection documents, backend services, and Kysely tables. It is not an
implementation backlog; rows that mention host policy or provider behavior are
integration boundaries for the consuming project.

Status legend:

- `ready-for-service`: public contract, backend behavior, UI where relevant,
  and storage shape are present. Host provider adapters, auth policy, and
  deployment guards may still be required.
- `contract-only`: types/routes/client/API slots exist, but UI or repository
  shape is incomplete.
- `partial`: some surfaces exist, but a likely MVP user flow is missing or weak.
- `missing`: no clear current surface.

This pass includes findings from two read-only sub-agent audits:
`api-first-surface-audit` and `ui-first-flow-audit`.

## Database And Collection Coverage Notes

- Cart lines, wishlist items, checkout lines, order lines, sellables, prices,
  coupons, entitlements, downloads, emails, webhooks, and account delete
  requests are intentionally JSON inside EmDash collections.
- `mika_stock_items` is the only current authoritative SQL stock counter table.
- `mika_stock_events` is the SQL stock reservation/movement/idempotency ledger.
- `mika_ephemeral_records` is the SQL home for tokens, rate-limit buckets,
  locks, nonces, and expiring operational records.
- No current SQL table stores cart lines or order lines; tests should treat
  those as aggregate JSON unless we intentionally change the architecture.

## High-Risk Gaps To Turn Into Tests First

1. Variant and price selection: one product with two sellables and two prices
   each should produce stable `purchase` values and normalize to the intended
   `sellableId`/`priceId`.
2. Quantity/max-per-order: add/update forms expose the current cap; services
   must still enforce `AvailabilityDTO.maxPerOrder`.
3. Checkout start: cart checkout and buy-now checkout should both accept
   customer fields and produce the same checkout DTO shape.
4. Stock reservation: checkout start must atomically reserve finite stock and
   fail with `OUT_OF_STOCK` without mutating cart JSON.
5. Token consume: magic-link and download tokens must be consumed atomically
   once, reject expired tokens, and not leak account existence.
6. Webhook idempotency: duplicate provider event IDs or payload hashes must not
   double-create orders, entitlements, emails, or stock movements.
7. Cart/wishlist merge: login/magic-link merge needs deterministic conflict
   behavior for duplicate sellables, prices, quantities, and currencies.
8. Safe redirects: every `returnTo`, portal return, checkout success, and cancel
   user input must pass through the shared safe-return helper.
