# Review: U08 / `76e2ef4` — Admin operationKey existence test

**Commit:** `76e2ef4abd93dd1cd14d449d37d284b6f3da4190`  
**Checkmark:** P1.3 Admin `operationKey` existence test  
**Scope:** `test/admin-operation-keys.test.ts` (+29 lines, new file)

## Summary

Adds a focused runtime pin: every `mikaAdminActionRuntimeDefinitions[actionId].operationKey` must exist on `mikaOperationDefinitions`. That is exactly what ROADMAP P1.3 / EXECUTION U08 asked for (admin keys cannot dangle against the operation registry).

The type-level guard already exists in `src/api/admin-action-runner.ts`:

- `MikaAdminActionRuntimeDefinition.operationKey: keyof typeof mikaOperationDefinitions`
- `mikaAdminActionRuntimeDefinitions: Readonly<Record<MikaAdminActionId, …>>` with `MikaAdminActionId = keyof typeof mikaAdminActionDefinitions`

So a misspelled or removed operation key fails typecheck today. The new test is intentional belt-and-suspenders: clearer failure text (`actionId → operationKey`), and residual protection if the type pin is loosened or bypassed with casts. Commit message accurately describes this as complementing the `keyof typeof` pin.

Relative to the golden snapshot in `test/index.test.ts` (“resolves admin action operations from internal runtime metadata”), this test is more maintainable for pure existence: it does not hardcode the action→key table, so adding an admin action only requires updating the runtime map (and typecheck), not a second expected array here. The golden test still covers operation *names* / facade resolution and remains complementary.

**Verdict:** Accept. Closes P1.3 admin existence / U08 as specified. One weak second case should be tightened so the suite does not claim more than it checks.

## Issues

### Issue 1 -- Severity: suggestion
- File: `test/admin-operation-keys.test.ts:21-29`
- Description: The case titled “covers every MikaAdminActionId with a runtime definition” does **not** pin against `MikaAdminActionId` / `mikaAdminActionDefinitions`. It only does:

  1. `Object.keys(mikaAdminActionRuntimeDefinitions)` non-empty  
  2. for each of those keys, `mikaAdminActionRuntimeDefinitions[key]` is defined  

  That is a tautology over the same object. It would still pass if the runtime map silently dropped an action id (were the `Record<MikaAdminActionId, …>` annotation ever weakened), and it never imports the UI definition map that actually defines `MikaAdminActionId`.
- Suggestion: Assert key-set equality against the UI registry, e.g.:

  ```ts
  import { mikaAdminActionDefinitions } from "../src/admin";

  it("covers every MikaAdminActionId with a runtime definition", () => {
    expect(Object.keys(mikaAdminActionRuntimeDefinitions).sort()).toEqual(
      Object.keys(mikaAdminActionDefinitions).sort(),
    );
  });
  ```

  That matches the type-level `Record<MikaAdminActionId, …>` pin at runtime and makes the title honest. Optional: drop the case entirely if U08 is intentionally only the operationKey∈registry direction (first test alone satisfies the checkmark).
- Status: open

### Issue 2 -- Severity: nit
- File: `test/admin-operation-keys.test.ts:13`
- Description: Membership uses `definition.operationKey in mikaOperationDefinitions`. For a plain registry object this is fine today, but `in` also walks the prototype chain. Own-key checks are the usual style for registry pins.
- Suggestion: Prefer `Object.hasOwn(mikaOperationDefinitions, definition.operationKey)` (or `Object.prototype.hasOwnProperty.call(...)` if an older lib target is a concern). Failure reporting can stay the same.
- Status: open

## Out of scope (not issues)

- No reverse pin (admin-named ops that no admin action uses). P1.3 only requires keys used by the admin runtime map exist on the operation registry; orphan admin ops are allowed.
- No semantic check that admin actions only target `admin*` operations (e.g. pointing an action at `cart.add` would still pass existence). Type pin allows any operation key by design.
- Overlap with `test/index.test.ts` golden admin wiring is acceptable: existence vs exact name table serve different failure modes.
