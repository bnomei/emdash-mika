**Verdict:** Accept for P0.1 / U02 as specified. Known gaps are closed; current input surface is fully re-exported and equality-pinned. Residual issues are about **how strongly** future omissions are enforced (process list vs discovery), not about incomplete delivery of the two named inputs.

## Issues

### Issue 1 -- Severity: suggestion
- File: `test/types-barrel-completeness.ts`
- Description: Completeness is a **hand-maintained triple** (API import list, barrel import list, `PublicOperationInputPairs` map). The header correctly says new public `*Input`s must extend both lists and the map. That means:

  1. Add `FooInput` to `api/types` (or validation) **and** re-export it from `src/types/index.ts`, but
  2. **forget** to extend this test,

  and typecheck still passes. The commit body claim that “future input omissions fail typecheck” is true for **listed** names that later leave the barrel (or diverge in type), but **not** for **newly introduced** `*Input` names omitted from the pin. Relative to “every operation-facing `*Input` on the wire surface,” the armor is process-dependent rather than discovery-based.
- Suggestion: Prefer a key-discovery pin so the set of `*Input` names is derived from the modules, e.g. `import type * as Api` / `import type * as Barrel`, remap keys with `K extends \`${string}Input\``, then `Exclude<keyof ApiInputs, keyof BarrelInputs>` / equality per key must be `never` / `true`. Keep the file’s intent; drop the triple list. If namespace `import type *` is awkward with mixed value exports, a single generated or `satisfies`-style map of known names is still better only if CI also diffs against `export type { …Input }` in `api/types`.
- Status: open

### Issue 2 -- Severity: suggestion
- File: `test/types-barrel-completeness.ts` (imports); compare `test/package-exports.ts`
- Description: Completeness imports the barrel via **source** path `../src/types/index`, not the published subpath `@bnomei/emdash-mika/types`. That correctly locks source re-export equality under `test/tsconfig.json` (Bundler resolution), but it does **not** prove the **package export map** + `dist` `.d.mts` surface for the full input set. Only `CheckoutCancelInput` / `CheckoutStatusInput` are package-path-pinned in `package-exports.ts` (under `types:check` / NodeNext). A regression that breaks package export wiring for some other input while leaving `src/types/index.ts` intact would not be caught by the completeness file.
- Suggestion: Optionally re-import the barrel side of the pin from `@bnomei/emdash-mika/types` (and run that file under the package-exports tsconfig, or add a thin package-path twin). Source-relative equality can remain as a fast unit; package-path is what hosts resolve. Minimum bar already met for the two historical gaps.
- Status: open

### Issue 3 -- Severity: nit
- File: `test/types-barrel-completeness.ts:144-146`
- Description: Failure mode is `AllTrue<PublicOperationInputPairs>` where a bad pair becomes `never`. TypeScript reports that `never` is not assignable to `true` on the whole mapped type; the **which key** signal is weaker than a per-pair `ExpectTrue<AssertEqual<…>>` alias (or a `const _check: PublicOperationInputPairs = { …: true }` object). Fine for a small fixed list; slightly worse DX as the map grows.
- Suggestion: If the file stays hand-listed, use one `type _CheckoutCancelInput = ExpectTrue<AssertEqual<…>>` (or similar) per name so the failing line names the input. If Issue 1’s discovery approach is adopted, encode missing keys in the error type (`Missing: Exclude<…>`).
- Status: open

### Issue 4 -- Severity: nit
- File: `test/package-exports.ts:207-209`
- Description: Comment says “Public operation inputs previously missing from the `/types` barrel.” Accurate historically; after U02 those fields are ordinary contract pins, not “previously missing” forever. Harmless.
- Suggestion: Soften to “Public checkout status/cancel operation inputs on `/types`” (or drop the “previously missing” clause) on the next touch.
- Status: open
