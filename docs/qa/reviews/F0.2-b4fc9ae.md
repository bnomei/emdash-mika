## Summary

F0.2 does what the card asked: stop using generic `CONFLICT` for pure idempotency-payload mismatch, stock reservation undercut, and deferred webhook processing, while leaving genuine concurrency / in-progress / inventory-math races on `CONFLICT` (or existing specific codes like `OUT_OF_STOCK`).

## Issues

### Issue 1 — Severity: **low** (classification residual / client branching)

- **Area:** Admin stock adjust · `would_go_negative` vs `would_undercut_reserved`
- **File:** `src/api/backend/factory.ts` (mapping of `AdjustStockRepositoryResult`)
- **Description:**  
  After F0.2:

  | Repository status | Emitted code |
  | ----------------- | ------------ |
  | `would_undercut_reserved` | `STOCK_CONFLICT` |
  | `would_go_negative` | `CONFLICT` |

  Both are CAS-mutation failure modes from `StockRepository.adjustStock` / `stockAdjustmentFailureStatus`. The card’s definition of `STOCK_CONFLICT` is “stock CAS undercut / concurrent reservation failure,” which **exactly** matches undercut-reserved. The types comment on `STOCK_CONFLICT` (“undercut concurrent reservation **or adjustment**”) is slightly broader and could be read to include negative-on-hand adjust races.

  Leaving `would_go_negative` on `CONFLICT` is **defensible**: it is inventory arithmetic (on-hand would go below zero), closer in spirit to a hard stock floor than to “would steal from active reservations.” It also avoids over-mapping every stock 409 onto `STOCK_CONFLICT` (card **Do not**: auto-map every 409).

  Residual cost: admin UIs that want “retry / refresh stock after concurrent adjust” must still treat **both** `STOCK_CONFLICT` and some `CONFLICT`s (message- or context-specific) unless they only care about reservation undercut.

- **Suggestion (optional follow-up, not required to close F0.2):**  
  Either document the split explicitly next to the factory mapping / README Errors section, **or** migrate `would_go_negative` → `STOCK_CONFLICT` if product wants a single admin stock-CAS code. Prefer documentation over another soft break if hosts already started branching on `STOCK_CONFLICT` for undercut only.
- **Status:** open residual — **does not block F0.2**

### Issue 2 — Severity: **nit** (ACP projection fidelity; pre-existing map)

- **Area:** `STOCK_CONFLICT` → ACP `out_of_stock` (`src/acp/mappers.ts`)
- **Description:**  
  Now that `STOCK_CONFLICT` is actually emitted, any path that projects Mika failures through ACP still collapses it with `OUT_OF_STOCK`. That is fine for shopper-facing “cannot sell” UX, but loses the reservation-undercut vs sold-out distinction for agent clients. Checkout reserve paths correctly use `OUT_OF_STOCK` already; the new emission is primarily admin stock adjust, which is rarely ACP-facing.
- **Suggestion:** No change required for F0.2. If agents ever drive stock admin, consider a distinct ACP code or keep admin off ACP.
- **Status:** acknowledged pre-existing; out of F0.2 emission scope

## Non-issues / confirmed correct

- **In-progress ≠ mismatch:** `checkoutIdempotencyInProgress` and admin “already in progress” / “completed but unsafe to replay” remain `CONFLICT`. Retry policy differs from “use a new key because payload diverged.”
- **Cart CAS left alone:** locked cart, version conflict, create race stay `CONFLICT` — genuine concurrency, not idempotency payload mismatch.
- **Checkout reserve insufficient stock stays `OUT_OF_STOCK`:** concurrent under-subscription of sellable availability is shopper inventory failure, not admin reservation undercut (`STOCK_CONFLICT`).
- **Webhook deferred product semantics:** `webhookReceiptResult` returns `WEBHOOK_DEFERRED` when payment/subscription webhooks remain `status: "received"` (accepted, not finished) — matches “accepted-but-deferred; retry delivery,” not a hard conflict.
- **Status discipline:** Migrated failures keep 409; enum still includes `CONFLICT`.
- **Test discipline:** Backend tests pin codes for stock adjust undercut/idempotency, checkout input mismatch, admin refund key reuse, and multiple webhook deferred races.
